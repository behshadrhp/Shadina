# 15. مرور امنیتی

این صفحه رفتار مرتبط با امنیت را که در کد مشاهده شد خلاصه می‌کند. یافته‌های تفصیلی، شواهد و رفع در
[گزارش مرور امنیتی](../reports/security-review.md) آمده است.

## دامنه و روش

- مرور استاتیک همه فایل‌های Go، SQL، پیکربندی و Swagger.
- بررسی‌های زمان اجرای فقط-خواندنی روی API محلی و دیتابیس PostgreSQL توسعه.
- بدون تست نفوذ، fuzzing، اسکن آسیب‌پذیری وابستگی (`govulncheck` در دسترس نبود)، بررسی پیکربندی تولید یا
  تست بار.
- یافته‌ها محدود به آنچه مخزن و زمان اجرای محلی نشان می‌دهند هستند. نبود یک یافته ادعای امن‌بودن سیستم نیست.

## خط پایه امن مشاهده‌شده

| کنترل | پیاده‌سازی |
|---|---|
| ذخیره رمز | bcrypt با `bcrypt.DefaultCost`؛ هش‌ها در `bytea`؛ JSON رمز را حذف می‌کند |
| مقاومت تزریق SQL | همه کوئری‌ها از پارامتر `$1` استفاده می‌کنند؛ `pq.Array` برای آرایه‌ها؛ بدون الحاق SQL کنترل‌شده توسط کاربر |
| محدودیت الگوریتم JWT | `WithValidMethods(HS256)` به‌علاوه بررسی تابع کلید HMAC |
| issuer/audience/انقضای JWT | `WithIssuer`، `WithAudience`، `WithExpirationRequired`؛ `nbf` توسط jwt/v5 اعتبارسنجی می‌شود |
| محدودیت بدنه درخواست | `MaxBytesReader` ۱ MiB |
| فیلدهای JSON ناشناخته | رد می‌شوند |
| تایم‌اوت‌های سرور HTTP | خواندن ۱۰ ثانیه، نوشتن ۳۰ ثانیه، بیکاری ۱ دقیقه |
| محدودیت pool DB | حداکثر open/idle برابر ۳۰، زمان بیکاری ۱۵m |
| پارامتری‌سازی DB | بله، شامل جست‌وجوی فید |

این‌ها خط پایه‌های محکمی هستند، اما چند مشکل مجوزدهی، پیکربندی و مدیریت خطا باقی مانده است.

## خلاصه یافته‌ها

| شناسه | شدت | یافته | وضعیت |
|---|---|---|---|
| SEC-01 | بالا | راز JWT fallback hard-code دارد و اعتبارسنجی راه‌اندازی ندارد؛ کلید env غلط‌املا `AUTH_SECRET_KAY` است | تأیید با کد/پیکربندی |
| SEC-02 | بالا | شاخه دسترسی پست ادمین `next` را صدا می‌زند و سپس 401 می‌نویسد، پاسخ را خراب می‌کند و ممکن است اجرا با نتیجه گمراه‌کننده را مجاز کند | تأیید با مسیر کد؛ با کاربر ادمین آزمایش نشد |
| SEC-03 | متوسط | خطاهای خام داخلی (parser JWT، SQL، strconv) به کلاینت برگردانده می‌شوند | محلی تأیید شد |
| SEC-04 | متوسط | JWT نامعتبر/منقضی HTTP 500 برمی‌گرداند، نه 401 | محلی تأیید شد |
| SEC-05 | متوسط | endpoint فید بررسی نمی‌کند که `userID` مسیر با کاربر احراز هویت‌شده یکی است | محلی تأیید شد |
| SEC-06 | متوسط | بدون ابطال توکن، refresh یا logout؛ توکن‌های bearer ۷۲ ساعته | شکاف طراحی |
| SEC-07 | متوسط | بدون محدودیت نرخ یا قفل ورود روی register/token | شکاف طراحی |
| SEC-08 | پایین | ثبت‌نام اعتبارسنجی قالب ایمیل ندارد و خطاهای تکراری/DB را افشا می‌کند | با کد تأیید شد؛ مسیر تکراری آزمایش نشد |
| SEC-09 | پایین | نشانه‌های شمارش کاربر برای ایمیل ناشناخته و رمز اشتباه متفاوت‌اند | با کد تأیید شد |
| SEC-10 | پایین | بدون CORS، TLS، هدر امنیتی یا سیاست request ID در برنامه | با کد/پیکربندی تأیید شد |
| SEC-11 | پایین | `context.WithValue` از کلید رشته built-in استفاده می‌کند؛ literal `"user"` در `GetUserCTX` | با staticcheck/کد تأیید شد |
| SEC-12 | پایین | `response.Respond` در شکست encode JSON مقدار `log.Fatalf` را صدا می‌زند | با کد تأیید شد |
| SEC-13 | پایین | `ReadHeaderTimeout`/`MaxHeaderBytes` تنظیم نشده‌اند؛ سخت‌سازی slowloris ناقص است | با کد تأیید شد |
| SEC-14 | اطلاعاتی | تزریق SQL یافت نشد؛ کوئری‌های پارامتری استفاده شده‌اند | با مرور تأیید شد |
| SEC-15 | اطلاعاتی | کاربران seed هش رمز خالی دارند و نمی‌توانند وارد شوند | در DB/API تأیید شد |
| SEC-16 | اطلاعاتی | Swagger UI عمومی است و آدرس spec آن اشتباه پیکربندی شده | با پیکربندی UI تأیید شد |

## رفع با بالاترین اولویت

1. **راز JWT قوی را در راه‌اندازی الزامی کنید.** `AUTH_SECRET_KAY` را به `AUTH_SECRET_KEY` تغییر نام دهید (با
   سازگاری عقب‌رو یا یادداشت مهاجرت)، fallback را برای محیط‌های غیرتوسعه حذف کنید و اگر راز غایب/ضعیف است
   سریع شکست بخورید.
2. **`UserPostAccessMiddleware` را اصلاح کنید.** بعد از `next.ServeHTTP` مقدار `return` بگذارید؛ برای اقدامات
   احراز هویت‌شده اما ممنوع 403 برگردانید؛ مجوزهای مدیر/ادمین را صریح تعریف کنید.
3. **بازگرداندن خطاهای خام را متوقف کنید.** خطاهای نوع‌دار و یک نگاشت‌کننده واحد معرفی کنید؛ موارد داخلی را با
   request ID لاگ و پیام عمومی به کلاینت برگردانید.
4. **برای توکن‌های نامعتبر 401 برگردانید.** جزئیات parser را افشا نکنید.
5. **دسترسی فید را تصمیم و اعمال کنید.** اگر فید خصوصی است، شناسه کاربر مسیر را با توکن مقایسه کنید؛ اگر
   عمومی است، مستند کنید و حذف JWT از آن مسیر را در نظر بگیرید.

## ویژگی‌های امنیتی پیاده‌سازی‌نشده

- چرخش refresh token، ابطال، logout، `jti`، مدیریت دستگاه/session.
- بازنشانی/تغییر رمز، تأیید ایمیل، MFA.
- محدودیت نرخ، قفل حساب، CAPTCHA.
- مدیریت نقش/مجوز فراتر از `role_id` عددی.
- لاگ audit تصمیم‌های authn/authz.
- سیاست CORS، خاتمه TLS، هدرهای امنیتی (CSP/HSTS/X-Content-Type-Options)، استراتژی CSRF برای کلاینت‌های
  کوکی‌محور (احراز هویت کوکی وجود ندارد).
- یکپارچه‌سازی secret manager/KMS.
- اسکن آسیب‌پذیری وابستگی، SAST/DAST، SBOM.
- پاک‌سازی ورودی فراتر از JSON/validator (خروجی JSON است؛ بدون رندر HTML).
- مدیریت آپلود فایل/رسانه (پیاده‌سازی نشده).

## محدودیت‌های تأیید

- هیچ کاربر ادمین وجود نداشت، بنابراین SEC-02 سرتاسری بازتولید نشد.
- تست توکن منقضی اجرا نشد؛ رفتار از همان شاخه خطای `ValidateToken` توکن‌های بدشکل پیروی می‌کند.
- هیچ مدل مهاجم خارجی، مرز شبکه یا راز تولید در دسترس نبود.
- `govulncheck` نصب نبود؛ هیچ ادعایی درباره CVEهای وابستگی مطرح نمی‌شود.
- ریسک fallback راز JWT به پیکربندی استقرار بستگی دارد؛ اگر همیشه راز env قوی تنظیم شود، fallback استفاده
  نمی‌شود. کد آن شرط را اعمال نمی‌کند.
