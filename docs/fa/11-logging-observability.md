# 11. لاگ‌نویسی و مشاهده‌پذیری

## راه‌اندازی لاگ

`cmd/api/main.go`:

1. `os.MkdirAll("logs", 0755)` — پوشه لاگ را نسبت به پوشه کاری فرآیند می‌سازد.
2. `zap.NewProductionConfig()` — encoder JSON، پیش‌فرض‌های تولید، sampling فعال.
3. `OutputPaths = ["logs/app.log"]`.
4. `ErrorOutputPaths = ["logs/error.log"]`.
5. `zap.Must(...).Sugar()`؛ `defer log.Sync()`.

`logs/app.log` ورودی‌های zap را از `app.logger` دریافت می‌کند. `logs/error.log` **مقصد خطای داخلی** zap است؛
به‌طور خودکار خطاهای برنامه را دریافت نمی‌کند. در زمان بررسی `logs/error.log` صفر بایت بود.

`defer log.Sync()` وقتی `main` از طریق `log.Fatal` پس از بازگشت `ListenAndServe` خارج شود اجرا نمی‌شود. همین
برای `db.Close()` صادق است. این می‌تواند ورودی‌های بافری لاگ را در خاموشی از دست بدهد.

## لاگ درخواست

`app.LoggerMiddleware` نویسنده پاسخ را با `middleware.NewWrapResponseWriter` می‌پیچد و پس از بازگشت هندلر
بعدی این‌ها را لاگ می‌کند:

| فیلد | مقدار |
|---|---|
| `msg` | `http request` |
| `method` | متد HTTP |
| `path` | `r.URL.Path` (query string لاگ نمی‌شود) |
| `remote_addr` | `r.RemoteAddr` (پس از `RealIP` در chi) |
| `status_code` | وضعیت پاسخ ثبت‌شده |
| `bytes` | بایت‌های نوشته‌شده |
| `duration` | `time.Since(start)` |

این موارد را **لاگ نمی‌کند**:

- شناسه یا نام کاربری احراز هویت‌شده
- request/correlation ID
- الگوی مسیر یا نام هندلر
- هدرهای درخواست (شامل `Authorization`)
- بدنه درخواست/پاسخ
- پارامترهای query (برای جلوگیری از نشت توکن در URL خوب است، اما عیب‌یابی را محدود می‌کند)
- خطاها (هندلرها خطا برمی‌گردانند بدون لاگ کردن آن‌ها)

`middleware.Logger` در chi نیز سراسری ثبت شده و یک خط common-log-format به stdout می‌نویسد. در اجرای معمول
ترمینال، این یک جریان لاگ دوم و بدون ساختار تولید می‌کند. در فرآیند detached ممکن است به service manager برود
یا از دست برود.

`middleware.Recoverer` panicها را بازیابی و stack trace را با لاگر استاندارد لاگ می‌کند. چون
`LoggerMiddleware` هندلرهای پایین‌دست را بعد از `Recoverer` می‌پیچد، panic از کد لاگ پس از هندلر در
`LoggerMiddleware` عبور می‌کند؛ لاگ درخواست سفارشی ممکن است برای درخواست‌های panic‌شده غایب باشد.

## قالب و سطح لاگ

- قالب: JSON تولیدی zap، مثلاً:
  ```json
  {"level":"info","ts":1790791373.617005,"caller":"api/main.go:84","msg":"database stable publish","driver":"postgres"}
  ```
- سطح: پیش‌فرض پیکربندی تولید (`info`)؛ بدون لاگر debug/توسعه در API.
- Sampling: sampling تولیدی zap به‌صورت پیش‌فرض فعال است؛ ورودی‌های یکسان مکرر ممکن است حذف شوند.
- چرخش: **هیچ**. بدون سیاست lumberjack/چرخش، محدودیت اندازه، نگه‌داری یا فشرده‌سازی. فایل رشد می‌کند تا
  چرخش خارجی پیکربندی شود.
- خروجی: فقط فایل برای zap؛ لاگ‌های chi/stdlib به stdout/stderr می‌روند.
- مجوز پوشه/فایل: `logs` با `0755` ساخته می‌شود؛ حالت فایل تابع umask فرآیند است.

## چه چیزی در راه‌اندازی لاگ می‌شود

- `database stable publish` با `driver` (نه DSN).
- `server stable` با `address` (مقدار `SERVER_URL`، مثلاً `127.0.0.1:8000`) و `environment`.
- خطاهای کشنده راه‌اندازی از طریق `log.Fatalln` (لاگ استاندارد، stderr): شکست بارگذاری `.env`، شکست اتصال DB.

پیام لاگ سرور `address` می‌گوید اما از `app.config.url` (`SERVER_URL`) استفاده می‌کند، نه `app.config.addr`
(`SERVER_ADDR`). اگر متفاوت باشند، لاگ گمراه‌کننده است.

## چه چیزی لاگ نمی‌شود

- موفقیت/شکست احراز هویت (به‌جز کد وضعیت در لاگ درخواست).
- رد مجوزدهی (فقط وضعیت 401/بایت‌ها).
- خطاهای SQL یا کوئری‌های کند.
- جزئیات شکست اعتبارسنجی (به کلاینت برگردانده می‌شوند، لاگ نمی‌شوند).
- جزئیات panic در لاگ سفارشی zap (Recoverer از لاگ استاندارد استفاده می‌کند).
- ردپای audit برای تغییرات پست/کاربر.
- نتایج health-check یا تأخیر DB.
- نتایج مهاجرت/seed (seed از `log` استاندارد استفاده می‌کند).

## شکاف‌های مشاهده‌پذیری

| قابلیت | حاضر؟ | یادداشت |
|---|---|---|
| لاگ ساخت‌یافته | جزئی | Zap JSON برای درخواست/راه‌اندازی؛ لاگ‌های بدون ساختار chi/stdlib جای دیگر. |
| request/correlation ID | خیر | بدون میان‌افزار، هدر یا مقدار context. |
| متریک | خیر | بدون متریک Prometheus/StatsD/OTel. |
| ردیابی توزیع‌شده | خیر | بدون OpenTelemetry/Jaeger. |
| ردیابی خطا | خیر | بدون یکپارچه‌سازی Sentry/Rollbar. |
| بررسی سلامت | جزئی | `/v1/health` استاتیک است؛ بدون بررسی DB/وابستگی. |
| بررسی آمادگی | خیر | همان health. |
| پروفایلینگ | خیر | بدون `net/http/pprof`. |
| لاگ کوئری | خیر | خطاهای `lib/pq` برگردانده می‌شوند اما مرکزی لاگ نمی‌شوند. |
| لاگ audit | خیر | بدون ثبت اینکه چه کسی چه چیزی را تغییر داد. |
| چرخش لاگ | خیر | چرخش خارجی لازم است. |
| داشبورد/هشدار | خیر | بدون پیکربندی در مخزن. |

## endpointهای سلامت

| مسیر | نوع | رفتار |
|---|---|---|
| `GET /ping` | ضربان | میان‌افزار chi؛ 200 `text/plain` بدنه `.`؛ روتر را دور می‌زند. |
| `GET /v1/health` | زنده‌بودن برنامه | 200 JSON `{status:"ok",version,environment}`. به PostgreSQL دست نمی‌زند. |

هیچ‌کدام probe آمادگی برای دیتابیس نیست. استقرار می‌تواند ترافیک را به نمونه API با DB خراب مسیر دهد. به
[12. Docker و استقرار](12-docker-deployment.md) مراجعه کنید.

## مدیریت داده حساس

بر اساس مرور کد:

- هدرهای `Authorization` و بدنه‌های درخواست توسط میان‌افزار سفارشی یا لاگر chi لاگ نمی‌شوند.
- query stringها توسط میان‌افزار سفارشی لاگ نمی‌شوند (از `URL.Path` استفاده می‌کند)، که ریسک نشت توکن را
  کاهش می‌دهد.
- `remote_addr` (IP کلاینت) لاگ می‌شود؛ لاگ‌ها را داده شخصی بالقوه تلقی کنید.
- پاسخ‌های خطا می‌توانند جزئیات دیتابیس/parser داشته باشند، اما به کلاینت فرستاده می‌شوند، نه توسط
  کمک‌تابع‌های پاسخ در `app.log` نوشته شوند.
- مقصد خطای Zap لاگ خطای برنامه نیست؛ فرض نکنید خطاها آنجا ظاهر می‌شوند.
- هیچ لایه ماسک/redaction وجود ندارد. اگر لاگ‌نویسی آینده هدر/بدنه/فیلد کاربر اضافه کند، ابتدا redaction
  اضافه کنید.

## فرمان‌های عملیاتی

```bash
# دنبال کردن لاگ‌های ساخت‌یافته درخواست (فقط خواندنی)
tail -f logs/app.log

# دنبال کردن لاگ‌های کانتینر دیتابیس (فقط خواندنی)
docker compose logs -f postgresql

# بررسی شنود API
curl -sS http://127.0.0.1:8000/v1/health
curl -sS http://127.0.0.1:8000/ping
```

هیچ فرمان چرخش لاگ مستندشده در مخزن وجود ندارد. در استقرار واقعی از logrotate/درایور لاگ کانتینر خارجی
استفاده کنید.

## توصیه‌ها

1. میان‌افزار request ID اضافه کنید؛ آن را در هر خط لاگ و پاسخ خطا بگنجانید.
2. لاگ خطای ساخت‌یافته با `zap.Error(err)` و request ID اضافه کنید.
3. شناسه/نقش کاربر احراز هویت‌شده را در مسیرهای محافظت‌شده لاگ کنید (نه توکن).
4. آمادگی آگاه به DB (`PingContext` با تایم‌اوت کوتاه) جدا از زنده‌بودن اضافه کنید.
5. متریک برای تعداد/مدت/وضعیت درخواست، آمار pool DB و کدهای خطا اضافه کنید.
6. ردیابی OpenTelemetry حول HTTP و SQL اضافه کنید.
7. چرخش/نگه‌داری لاگ اضافه کنید یا لاگ‌ها را به سیستم متمرکز بفرستید.
8. `log.Fatal` در مسیر سرور را با خاموشی آرام و flush لاگ جایگزین کنید.
9. از `err.Error()` در پاسخ‌ها پرهیز کنید؛ آن را داخلی لاگ کنید.
10. سیاست نگه‌داری/redaction برای IP و شناسه کاربر مستند کنید.
